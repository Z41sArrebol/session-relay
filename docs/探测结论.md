# Z-Code 数据接入探测结论

> 探测时间：2026-10-18
> 范围：只读检查本机 `~/.zcode/cli/db/db.sqlite` 的表结构、字段与最小样本；参考本地 Magpie `internal/sessions/zcode.go`、`calls_zcode.go`、`opencode.go`（仅阅读，未修改、未复制代码）。没有读取或输出登录凭据、其他会话正文、密钥。

## 1. 能拿到什么

| 能力 | 结论 | 证据 |
|---|---|---|
| 会话列表 | 可以 | `session` 表：`id / parent_id / directory / title / title_source / task_type / time_created / time_updated / version / project_id` |
| 工作目录 | 可以 | `session.directory`，例如 `%USERPROFILE%\Desktop\<workspace>` |
| 用户消息 | 可以 | `message.data.role='user'`；真实输入过滤 `semantics.origin='real_user'` 且非 `model-only` |
| 模型公开回复 | 可以 | `message.data.role='assistant'`；正文在 `part.type='text'` |
| 工具调用 | 可以 | `part.type='tool'`：`tool`、`callID`、`state.input`、`state.status`、`state.output/error` |
| 工具执行结果 | 可以 | 同上 `state.output`；另有 `tool_usage` 表的 `exit_code / duration_ms / status / read_only / destructive / output_bytes` |
| 时间 | 可以 | 毫秒时间戳：`time_created / time_updated / started_at / completed_at` |
| 模型 | 可以 | `model_usage.provider_id / model_id / variant / agent`；消息里也有 `modelId / providerId` |
| Token | 可以 | `model_usage` 与 `turn_usage`；`part.type='step-finish'.tokens` |
| 运行状态 | 可以 | `turn_usage.status`、`tool_usage.status`、assistant 消息的 `time.completed` |
| 子 Agent | 可以识别 | 子会话 `session.parent_id` 指向父会话；`task_type='subagent_child'` |

**采集范围约定**：只采集 `real_user` 用户输入、`text` 公开回复、`tool` 调用与结果、`tool_usage` / `turn_usage` / `model_usage` 元数据。`reasoning` part 不采集；`metadata.visibility='model-only'` 的注入消息不当作真实用户要求。

## 2. 字段含义（已核对）

- `message.sequence`：**会话内**递增序号，不是全局序号。它是时钟偏差时的重要兜底。
- `part.sequence`：**消息内**序号。
- `message.time_updated` / `part.time_updated`：流式写入时会原地更新，因此不能只按“最大 id”做增量。
- `message.data.semantics.origin`：`real_user` 为真人输入，`agent_runtime` 为运行时注入。
- `model_usage.input_tokens`：**包含**缓存读取（AI SDK 口径）；`cache_read_input_tokens` 是其中已缓存部分。`output_tokens` 含 `reasoning_tokens`。
- `tool_usage.read_only / destructive / approval_status`：Z-Code 自己记录的工具安全属性。
- `session.title_source='default'` 时标题是默认值，前端标注“未命名”，不当作会话命名。
- `session.time_archived`：非空表示已归档。

## 3. 增量读取：现在凭什么说“可靠”，以及边界

实现采用四层机制，而不是只靠一个时间窗口：

1. **时间水位 + 15 秒重叠**：读取 `time_updated > watermark - 15s`，主键 upsert，内容指纹去重。
2. **会话内消息序号水位**：额外读取 `message.sequence > lastSequence - 2`，即使新消息的时钟比水位旧也能补到；对应消息的 part 通过 `message_id` 子查询一起补读。
3. **未完成记录每轮复查**：`status='running'` 或 `completed_at IS NULL` 的 `tool_usage / turn_usage / model_usage` 每轮都重读，不依赖水位。
4. **进行中的 assistant 消息每轮复查**：没有 `time.completed` 的 assistant 消息及其 part 每轮重读；工具 part 的 `state.status in ('running','pending')` 也会重读。

已用隔离 fixture 验证：长任务跨水位、并行工具、流式原地更新、暂停/恢复、重启补读、跨会话隔离、可选表缺失降级。15 秒重叠不是“绝不漏数据”的数学保证；保证来自“序号兜底 + 未完成记录复查 + upsert 去重”。

## 4. 外部启动 / 发送入口

- **没有找到官方文档化的 CLI 或本地 API**。Z-Code 是 Electron 桌面应用，安装目录只有 `ZCode.exe`，PATH 中没有 zcode 命令。
- 应用包内存在 `zcode://` 协议与内部 `/api/sessions` 字符串，但这是未公开的内部实现；按要求**不破解、不复用**，也不写 `session_input` 表伪造发送。
- 因此：**“向 Z-Code 目标会话直接发送”第一版不支持，明确降级为导出交接包 + 复制接力指令。**
- Claude Code CLI 已确认存在，支持 `-p/--print`、`--output-format json`、`--permission-mode plan|acceptEdits`。但**只验证了参数和进程启动，没有执行一次真实的“发送→接收→返回确认”往返**，所以连接器状态是 **候选（未验证）**，不是已验证连接器。
- 代码里实现了自检流程：发送固定文本 `RELAY_CONNECTOR_OK`，只有退出码 0、JSON `is_error=false` 且返回内容包含该标记，才写入 verified。自检必须由用户显式确认；当前没有执行，因此界面仍显示“候选 · 未验证”。

## 5. 已验证 / 推测

**已实际验证（本机）**
- 只读打开真实 Z-Code SQLite，列出 165 个顶层会话与工作目录。
- 读取真实会话的用户消息、公开回复、工具调用与结果、模型与 Token、turn/tool 状态。
- 真实会话演示：11 条用户、59 条公开回复、216 条工具记录，导出 287 行时间线；包内 8 个文件、约 1.35 MB。
- 流式写入中的会话可被读取；`message/part.time_updated` 会原地变化。
- Electron 44 运行时中 `better-sqlite3` 可只读打开该库（Node 20 直接加载会崩溃，测试改用 `ELECTRON_RUN_AS_NODE` 运行）。
- 打包清单哈希与实际文件一致；敏感文件、超限文件、符号链接、越界路径均被排除。
- 真实会话包的时间线中检测到 1 处“API Secret Key”，来自测试 fixture 里故意写的假 Key；说明会话证据也会被扫描，但这类检测只是启发式。

**推断（未验证为官方契约）**
- 表结构属于 Z-Code 内部实现，升级后可能变化；程序做 capability 探测与降级，而不是假设永久稳定。
- `session_input` 看起来像输入队列，但没有公开写入契约，**不使用**。
- 子会话正文可读，但第一版只把子会话作为“存在子 Agent 活动”的信号，不展开其内部记录。

## 6. Token 统计口径

拿一个已结束会话对照：

| 来源 | 输入 | 输出 | 说明 |
|---|---:|---:|---|
| `turn_usage` 合计 | 4,570,933 | 90,651 | **只有 4 行**，79 次模型调用；长会话会裁剪，不能当总量 |
| `model_usage` 合计 | 10,697,079 | 123,852 | 79 次调用，逐 attempt |
| `step-finish` 合计 | 10,696,763 | 123,722 | 与 model_usage 差 316 / 130（0.003% / 0.1%） |

结论：

- **总量以 `model_usage` 为准**；`step-finish` 用于交叉核对；`turn_usage` 只用于判断当前 turn 是否在运行。
- 界面明确写：`input` 含 `cache_read`，`output` 含 `reasoning`；缓存与推理单独展示，**不重复相加**。
- 与 Z-Code UI 显示数字可能存在小差异（最后一步未完成、重试 attempt 等）；不宣称“完全一致”。

## 7. 结构降级

- 必需表：`session / message / part`，必需列逐列探测（含 `message.sequence`、`part.sequence`）。
- 可选表：`tool_usage / turn_usage / model_usage`，逐表逐列探测；缺表或缺列时对应能力标为 `false`，会话列表和时间线仍可用。
- 修复了一个真实漏洞：会话列表曾在判断 `model_usage` 是否存在之前就 `prepare` 查询，缺表会直接报错。现在先探测、再 prepare。
- 缺少 SQLite JSON1 时，关闭“未完成消息/工具中间状态复查”，并在结构详情里标注降级。

## 8. 对实现的约束

- 源库只读：`readonly: true`、`PRAGMA query_only=ON`；不 checkpoint、不改 WAL、不手动操作 `-shm`。
- 不自动扫描上传历史会话；必须用户在列表中显式选择接入。
- 不采集 `reasoning`；不把 `agent_runtime` 注入当成用户要求。
- 发送真实内容前必须预览并确认；Z-Code 目标不支持发送，界面明确显示“仅支持导出”。

## 9. 恢复简报可用的 Z-Code 信号

面向“会话卡住 / 额度耗尽 / 必须换工具”的恢复场景，以下字段可用：

- `todo` 表：`content / status / priority / position / time_updated`。本次样本中 `completed 428`、`pending 52`、`in_progress 26`（数据会随使用变化）。这是“还剩什么”最直接的信号。
- `turn_usage.context_exceeded`：当前样本全为 0，但列存在；为 1 时直接作为“上下文超限”危险信号。
- `turn_usage.cancelled_by_user`：样本中 59 个 turn 被用户取消。
- `turn_usage.error_type`：如 `turn_cancelled / unknown_error`。
- `model_usage.status / error_type`：`server_error / auth_failed / unknown / network_error / invalid_request / timeout` 等。
- `tool_usage.status / exit_code`：可按命令聚合失败次数，并判断同一命令后来是否成功。
- `session.time_updated`、`tool_usage` 时间、incomplete assistant 消息：用于判断“仍在执行但长时间无进展”。

恢复简报由确定性规则生成，不调用模型；它把这些信号整理成五问五答：最新目标、已完成与可核对证据、失败过的路线、工作区一致性、接手先做什么。AI 总结仍是可选草稿，不取代这些证据。
