# 调研与问题选择：Agent 会话恢复与接手

> 2026-10-20。来源分两类：GitHub 上 Claude Code / OpenCode / Gemini CLI / Cline 的 issue 与 discussion；以及 7 个最接近的 GitHub 项目的 README（通过 SSH 克隆离线阅读，见文末清单）。README 反映的是项目自称的功能，issue 反映的是用户实际遇到的问题，两者分开看。

## 一、issue 里的真实痛点，按使用时刻归类

### A. 会话失效那一刻，没法让原 Agent 写交接

- Cline Discussion #499：上下文超限后界面只剩 "Retry" / "Start new task"，输入框锁死，无法删掉撑爆的消息，无法让 Agent 先总结一下。原话："I can't remove it from the chat so I have to start a new one."
- Claude Code #54580：用户想要 hook 能拿到 context 百分比，好在接近上限时自动做 handoff；说明现在没有触发点。
- OpenCode #44798：临近上下文上限时 Agent 拒绝开始新任务，也没有自动 handoff；用户只能开新会话手动粘贴。状态：not planned。

**共性**：失效发生在 Agent 已经不能说话的时刻，交接必须由**旁观者**生成，不能依赖原 Agent 配合。

### B. 压缩/恢复保存的是“历史”，不是“当前有效状态”

- Gemini CLI #20803：`--resume` 恢复的是磁盘上未压缩的完整历史，压缩白做，可能直接溢出。已修复，但根因说明：磁盘格式存的是过程，不是当前状态。
- OpenCode #4102：压缩摘要“太轻，不足以当交接”，丢规则、丢当前任务、丢文件和错误记录；BUILD 模式接续跑偏。后来改成结构化 handoff 格式（intent/files/errors/pending/rules/next）。
- Claude Code #29890、#24906：压缩后丢工作知识，重试已否决的方案；接续提示还会覆盖用户的 CLAUDE.md 规则。

**共性**：恢复质量的单位是“当前有效状态”（目标、规则、失败路线、文件状态、下一步），不是“消息还在”。

### C. 用户要的是主动翻页，不是被动压缩

- Claude Code #54254：要 `/handover`——可编辑草稿、同目录开新会话、不背完整历史。原话："I decide when to turn the page"。closed（stale）。
- Claude Code #59492：合并 9 个请求要 `/restart` + `/handoff`；评论强调需要 hook 暴露 context 百分比，否则下游都在重造 wrapper。closed（stale），无官方回复。

**共性**：交接是用户主动的“翻页”，且接收端要能真正开一个新会话。

### D. 记得内容，但找不到那个会话

- Claude Code #77523：记得文件名/符号/报错/一句话，自动标题搜不到，只能手动搜 JSONL。
- Claude Code #85624：重启后 worktree 里的会话文件还在，但入口从历史搜索消失。

**共性**：搜索和找回是另一个独立痛点，不解决“接手”，只解决“找到”。

### E. 显示成功但实际没交付

- Claude Code #85066：子 Agent 任务主会话几秒后以 success 结束，Action 显示成功，实际没有产出。
- Claude Code #17646：还有待办时 Agent 停了，用户要反复输入“继续”。not planned。

**共性**：进程结束 ≠ 交付完成。外部观察器只能提示信号，不能证明完成。

## 二、相似项目各优化什么（README 口径，未逐个安装验证）

| 项目 | 优化的时刻 | 关键做法 | 对我们有用的部分 |
|---|---|---|---|
| agent-handoff | 换工具/换人后继续 | 完整会话+工具证据打包，接收端**导入为原生新任务**；Codex↔Claude 中立转录；导出前密钥扫描并阻断 | 唯一补到“接收端”的；“传真实会话不是手写摘要” |
| claude-compact-handoff | 压缩前后 | 三个 hook 时机（工作前提醒/回合结束问笔记/压缩瞬间机械快照/压缩后指路）；机械笔记不经过模型 | “快照不能依赖模型必须成功”是对的；只用 hook，不接收 |
| Entire CLI | 追查代码/继续工作 | Hook 把会话绑到 git commit，支持 checkpoint 恢复 | “这段代码为什么这样改”的归因，与我们 Git 证据重叠 |
| agentplay | 排查 Agent 走偏 | 会话回放到地图+时间线，读文件/重试/失败/子 Agent | 诊断时刻，不接续 |
| agent-sessions / CASS | 找回历史 | 跨 16+ 工具全文搜索；CASS 有面向 Agent 的 JSON 输出 | 搜索时刻已充分竞争 |
| agent-session-view | 回看/分享 | Claude/Codex 浏览过滤，导出 HTML/文本 | 只读浏览，最接近我们的时间线 |

**修正**：claude-compact-handoff 的 README 原话证实了我们的直觉——"The summary keeps roughly what was said and reliably loses why things were decided and what was already ruled out." 我们恢复简报里的“失败路线”正是补这个缺口。它的弱点也很清楚：依赖 hook 时机，压缩如果绕过 hook 就没有快照；而我们的只读采集不依赖 hook。

## 三、选定要系统解决的问题

> **会话已经失效（卡住/超限/额度耗尽/换工具）时，从本地记录生成一份接收端可信的恢复简报，并证明另一个 Agent 能靠它接着完成，不需要原会话配合。**

范围收窄：不做跨工具原生导入（agent-handoff 已做且维护成本高），不做全文搜索（已充分竞争），只做“失效会话 → 可接手”。

## 四、验收标准（不能是自评）

1. 隔离会话 + 真实 Git 项目 + 未完成任务。
2. 生成恢复包，**没有 AI 总结**（证明确定性信息足够）。
3. 真实 Agent（Claude Code CLI，另用一套会话）只做两阶段：独立验收 → 继续实现。
4. 判定：
   - 验收阶段提出的问题能被包内证据回答（没有必须问发送方的缺口）；
   - 实现阶段产出的代码编译且测试通过；
   - 最终状态没有重复已否决的失败路线（包里有记录、Agent 没有重做）；
   - 全程记录在同一目录，可复查。
5. 如果缺信息，先改简报，不改实验。

## 五、与 session-relay 现状的差距

- 已满足：失效不依赖原 Agent（只读）、机械证据（Git/工具/待办）、失败路线分层、可信度门槛。
- 未满足：最后一步接手验证（本轮补）；接收端需要手动粘贴（Z-Code 无入口，Claude 连接器候选未验证）；没有可安装包。
